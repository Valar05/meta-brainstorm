# Fruit Density

**Date:** 2026-09-14
**Status:** active doctrine / autobiographical pattern

## Observation

Drew reports that the games he considers most complete and most perfect are disproportionately tiny: often one screen, one mechanic, and made in less than a week.

At the same time, the majority of development labor has historically gone into much larger games that produced less satisfying fruit.

This suggests a recurring inversion:

```text
more scope != more value
more labor != more joy
more systems != more consequence
```

The relevant quantity may be **fruit density** rather than project size.

```text
FRUIT DENSITY
= meaningful contact
+ legible consequence
+ adaptive possibility
  divided by
  production burden + connective tissue + maintenance drag
```

The exact formula is metaphorical, not a calibrated metric. The useful point is comparative: some tiny games deliver a very high concentration of the experience Drew actually values.

## Contact / consequence / adapt connection

A one-screen, one-mechanic game can compress the loop:

```text
CONTACT -> CONSEQUENCE -> ADAPT -> CONTACT
```

There is little travel between intention and result. The mechanic does not need a large world to become deep if each contact changes the next decision.

Larger projects often accumulate low-fruit connective tissue:

- content needed mainly to justify scale;
- menus, progression, persistence, and infrastructure;
- transition spaces and repeated setup;
- asset breadth that increases maintenance without increasing causal density;
- long production arcs before the core pleasure can be touched again.

None of these are inherently bad. The warning is that they can consume most of the budget while contributing little to the thing Drew actually wanted.

## Armor Command: expansion that earned permission

Armor Command is a useful counterexample to any simplistic rule that small games should never grow.

Its first public-ready form was already a compact, phone-first one-screen loop: tap to launch interceptors, hold to spray gunfire, survive escalating pressure, and upgrade between waves. The core only became fun once missile reload rhythm, gunfire, and incoming pressure visibly negotiated with each other.

Expansion then happened through **felt consequences of the existing loop**, not through an abstract demand for more content:

- independent missile-rack cooldowns made upgrades mechanically visible;
- the gun filled the downtime created by missile reloads;
- drop pods introduced a branching consequence: destroy the pod now or inherit a paratrooper problem later;
- paratroopers and rockets forced attention to split rather than merely increasing enemy numbers;
- the kill-chain turned clean contact into visible and audible score pressure;
- additive weapon mutations let one successful contact accumulate richer consequences without replacing earlier earned behavior.

The v1.0 devlog explicitly describes the drop pod as "the enemy that opened the game" and still concludes that the game remains compact, with compactness as part of its strength.

This suggests a stronger rule than "do not expand":

```text
SMALL GAME
-> prove contact/consequence loop
-> add one consequence-bearing extension
-> test whether the loop becomes richer
-> keep only if fruit density survives or rises
```

Armor Command grew because the small game kept granting permission.

## Expansion permission test

A proposed addition should answer at least one of these questions:

```text
Does it create a new meaningful contact?
Does it make an existing contact produce a more interesting consequence?
Does it force a genuinely different adaptation?
Does it preserve or improve the ratio of delight to production burden?
```

If the answer is no, the addition is probably scale manufacturing itself.

If the answer is yes, growth can be legitimate even when the artifact began as a one-screen toy.

The important distinction is therefore not:

```text
small = good
large = bad
```

It is:

```text
causal growth = potentially fruitful
obligatory growth = expensive distance
```

## Design consequence

The default unit should not be "the next large game."

It should be the smallest shippable artifact whose core loop already contains enough fruit to justify itself.

If a one-screen mechanic is delightful, expansion is optional.

If expansion lowers fruit density, stopping may be the higher-quality decision.

If expansion creates new contact, consequence, or adaptation while preserving the core, the small game may legitimately invite another layer.

## Engine consequence

The capability engine should make tiny finished artifacts extremely cheap to produce. This lets ideas be tested at their natural size instead of being forced to become large projects in order to feel legitimate.

A mature engine should therefore increase **fruit per unit labor**, not merely total possible scope.

Armor Command adds a second requirement: the engine should also make *earned expansion* cheap, so a tiny artifact can grow when reality demonstrates that the next layer is fruitful rather than because a roadmap demands it.

## Compact doctrine

> **The perfect game may be smaller than the work required to explain why it is enough.**

> **Do not spend ninety percent of the labor manufacturing distance between contact and consequence.**

> **Expansion is allowed when the existing game asks for it through play.**
